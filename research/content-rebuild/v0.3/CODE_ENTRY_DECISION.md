# 代码准入判断 v0.1

## 结论

**`CONDITIONAL PASS FOR A SEPARATE NARROW IMPLEMENTATION BRIEF`**

v0.3 已满足“可以设计下一轮代码实施方案”的条件，但本文件不授权直接修改现有 H5。

## 已关闭的缺口

- 四个候选原型均有 2 条支持、1 条张力、1 条排除规则；
- 共享去重、时间、冲突和证据不足门已唯一化；
- 20 条规则具有固定 ID；
- 32 个无真人、无生日抽象夹具具有唯一预期；
- 四份内容快照能从规则职责映射回 D1—D6 与 E1—E6；
- 问题答案已被技术性限制为显化校准，不参与原型裁决。

## 仍未授权的事项

- 不得现在改写 `lib/signatures.ts`、`lib/calibration.ts`、`data/questions.ts` 或结果页；
- 不得把旧四路线类型换名后继续使用；
- 不得把 20 条规则直接硬编码成四个 `if`；
- 不得新增依赖、数据库、运行时大模型或持久化；
- 不得把四份内容快照宣传为已验证结果。

## 下一轮最小实施范围

下一轮实施方案只应包含：

1. 新建与现有运行时隔离的 `content-model-v0.1` 纯函数层；
2. 用抽象 `EvidenceGraph` 输入执行 20 条规则；
3. 加载 32 个 JSON 夹具并验证预期；
4. 输出原型状态、内容键和最多 3 个 `CalibrationFork`；
5. 暂不接入现有页面和真实生辰流程；
6. 通过后再单独决定是否替换 Demo 内容链路。

## 为什么不直接接 UI

现有 Demo 的核心逻辑是“命盘只起题、回答决定路线”，与本合同相反。直接在旧链路上打补丁会同时保留两套裁决权，形成不可审计的混合系统。

正确路径是先在隔离纯函数层证明：

```text
同一抽象证据输入
→ 唯一规则状态
→ 唯一冲突结果
→ 稳定内容键
```

再替换旧模型，而不是边运行边迁移。

## 回滚与停止条件

- v0.3 全部为新增文档与 JSON，可回滚到 v0.2 head；
- 若代码实现需要答题分数、隐性权重、第五原型或万能兜底，立即停止；
- 若 32 个夹具不能在无真实命盘数据下稳定执行，返回规则层，不接 UI；
- 若内容键组装重新退化成流程报告，代码即使全绿也不得进入页面。
